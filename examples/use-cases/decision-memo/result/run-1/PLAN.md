# Plan: DECISION.md monorepo decision memo

## Goal
Produce `DECISION.md` in the working-directory root: a one-page (250-700 word) decision memo for a six-person team weighing a move of three services into a single monorepo, structured exactly as `check_memo.py` requires, so that `python check_memo.py` exits 0. The memo must be honest about what is given (six people, three services) versus what is assumed, must endorse exactly one option, and must state its reasons as expected, conditional improvements rather than absolutes.

## Observable acceptance criteria
1. `python check_memo.py` prints `OK: DECISION.md, <N> words, sections ['Context', 'Options', 'Criteria', 'Recommendation', 'Risks', 'Next steps']` and exits 0.
2. Exactly six level-2 headings, in this order, with these exact texts (checker lowercases and requires an exact match, so no suffixes like 'Options considered' or 'Next Steps (30 days)'): Context, Options, Criteria, Recommendation, Risks, Next steps.
3. Options section has at least 3 lines beginning with `- ` (one per option: bold name plus a one-line summary). Plan uses exactly 3 options.
4. Criteria section contains a markdown table: header row with at least 5 cells (Option + >= 4 criteria), a separator row of the form `|---|---|...`, and one row per option (3 rows) with every option scored on every criterion.
5. Recommendation section contains the literal substring 'recommend' and endorses exactly one option (Option B). It may name and compare Options A and C, but no option other than B may be described anywhere in the memo as recommended, preferred, a fallback, or the choice under some other condition. If the stated assumptions fail, the memo says the decision is revisited and the memo is revised, not that another option wins by default.
6. Word count by the checker's regex (alphanumeric runs, which also counts table scores and the `---` separator cells) is between 250 and 700; target 460-570 to leave margin both ways after the added assumption and conditionality language.
7. No line starts with triple backticks; no inline code; no source code or literal shell/git commands anywhere.
8. `check_memo.py` and `AGORA-LOG.md` are byte-for-byte unchanged; the only new file is `DECISION.md`.
9. Content honesty checks (reviewer-verifiable by reading the memo): (a) the Context section explicitly labels the scenario details as working assumptions to be confirmed, including the assumption that ownership and repository access are shared across all six engineers; (b) the Recommendation is conditional on confirming cross-service coupling and tooling duplication; (c) the memo contains no absolute claims such as 'only B removes', 'eliminates', 'disappears', and no unsupported quantitative claims such as 'half the migration effort'; (d) the memo distinguishes coordinated repository changes from deployment coordination; (e) Next steps include validating CI coverage of shared dependencies before cutover; (f) no categorical claim about team or ownership boundaries is presented as fact; any ownership argument is explicitly tied to the stated assumption; (g) exactly one option is endorsed (see criterion 5).

## Concrete approach
1. Write `DECISION.md` with the Write tool, UTF-8, ASCII-only characters, no em dashes.
2. Content outline (approximate word budgets in parentheses):
   - Title: `# Decision memo: move our three services into one monorepo?` plus one short metadata line (date 2026-10-29, audience: the six-person engineering team, status: proposed). Level-1 heading is invisible to the checker.
   - `## Context` (~135): what is given: six engineers, three services, each in its own repository today. Then an explicit assumptions sentence, for example: 'The details below are working assumptions drafted for this memo and should be confirmed by the team before the decision meeting.' Then the assumed scenario: the services are an API, a background worker, and a web front end sharing a client library and a schema; the assumed pains are that cross-service changes need two or three coordinated pull requests, that lint, CI and tooling configuration drift between repositories, and that the shared client library suffers version skew. Add a third labelled assumption: that all six engineers contribute to all three services and that no repository has access restrictions the others lack (finding R2-2). State plainly that if the team finds coupling is low, tooling duplication is small, or ownership and access are not actually shared, the case for change weakens and the decision should be reopened.
   - `## Options` (~60): three `- ` bullets, each `**Name.** one-line summary`:
     - A. Keep three repos; add a shared tooling package and a cross-repo release checklist.
     - B. Full monorepo: all three services in one repo, one CI pipeline with path-based test selection.
     - C. Hybrid: merge the more tightly coupled API and worker; front end stays separate.
   - `## Criteria` (~75 incl. table): one legend sentence (scores 1-5, 5 is best, scores are the author's judgement under the stated assumptions), then table with columns Option | Cross-service change cost | CI and build time | Migration effort | Ownership and onboarding clarity | Tooling drift risk. Suggested scores: A = 2,5,5,3,2; B = 5,3,2,4,5; C = 4,4,3,3,3.
   - `## Recommendation` (~135): 'We recommend Option B, the full monorepo, conditional on the team confirming two assumptions: that most feature work genuinely spans two or more services, and that tooling and CI configuration is in fact duplicated across the three repositories.' Reasons, phrased as expected effects, not guarantees: B is expected to reduce the cost of coordinated repository changes the most, because a cross-service change becomes one reviewable change set; drift should fall substantially because one toolchain and one CI configuration are shared; migration is a bounded one-time cost compared with a recurring coordination tax; CI time can be contained with path filters. The ownership argument, if used, is tied explicitly to the assumption: 'Under the stated assumption that all six engineers already work across all three services with the same access, separate repositories do not mirror any real ownership boundary; if that assumption is wrong, this reason does not hold.' Do not write the categorical form 'with six people there is no team boundary worth mirroring' (finding R2-2). Add one explicit sentence distinguishing scope: a monorepo simplifies coordinated code changes and reviews, but it does not by itself coordinate deployments; services will still deploy separately and must remain compatible across versions during rollouts. One sentence each on why not A (it reduces drift but leaves cross-service changes split across repositories) and C (it helps the API-worker pair but leaves the front end in the same position as today), with no quantitative effort comparison. Only B is recommended. Close with: 'If the confirmation step in Next steps does not support these assumptions, we will withdraw this recommendation, rescore the options with the measured data, and reissue the memo.' Do not state that A (or C) becomes the preferred or fallback option (finding R2-1).
   - `## Risks` (~100): bullets, each risk plus mitigation: slower or flakier single pipeline (path-based triggers, caching); loss of history or permissions during import (history-preserving import spike, access review); larger blast radius of a broken main branch (required checks, fast revert); build-tool learning curve and lock-in (start with the existing tooling, defer a dedicated monorepo build tool); gaps in CI coverage of shared dependencies, where a change to the shared library passes its own checks but breaks a consumer (validate that CI for shared code runs the consumers' test suites before cutover); disruption during the cutover freeze (one-day freeze, announced in advance).
   - `## Next steps` (~95): numbered list with owner placeholders and dates relative to 2026-10-29: (1) confirm the assumptions by Nov 3: sample the last quarter of pull requests to measure how many spanned multiple repositories, compare the three CI and lint configurations for duplication, and check whether any repository has access restrictions or an owner the others do not share; (2) decision meeting by Nov 5: proceed with Option B if the assumptions hold; otherwise rescore the options with the measured data and reissue this memo (no automatic fallback to any option); (3) spike importing all three repos with history preserved by Nov 12; (4) CI with path-based triggers by Nov 19, including a check that changes to the shared library and schema trigger the test suites of every consuming service; (5) one-day freeze and cutover the following week only after that CI validation passes; (6) retrospective 30 days after cutover.
3. Run the proof command. If word count is off, adjust Context or Risks only; never touch headings or table shape. Do not shorten by removing the assumptions sentences, the conditionality clause, the ownership-assumption qualifier, the withdraw-and-reissue sentence, or the deployment-coordination sentence, since those are acceptance criterion 9.

## Key decisions and trade-offs
- Bulleted options instead of `###` subheadings: the checker slices sections with `text.index('## ' + heading)`, so any level-3 heading whose text equals a level-2 heading name (e.g. `### Risks` inside Options) would corrupt section boundaries. Bullets eliminate this failure class. Rule for the builder: no level-3 heading may reuse a level-2 heading's text.
- Exactly three options: satisfies 'at least three' while keeping the table and word count small; a fourth option adds ~40 words and little decision value.
- Five criteria rather than the minimum four: gives the recommendation a clear scoring story while costing only ~15 extra words.
- Numbers live only in the table; prose stays number-light. Table cells and separator dashes count as words, so the table is budgeted at ~60 words.
- No inline code or literal commands even though the checker only catches fenced blocks: the task says 'no source code', so git/CI mechanics are described in words.
- Assumptions labelled inside the memo rather than hidden in this plan (finding R1): the task gives only six people and three services, and the invented pains drive the recommendation. Readers of the memo must see which inputs are assumed, and the recommendation is made conditional on confirming the two assumptions that matter most: cross-service coupling and tooling duplication.
- Claims phrased as expected reductions, not elimination (finding R2): neither the task nor the scoring table supports 'only B removes' or 'drift disappears', and the 'half the migration effort' comparison for C had no basis. The memo uses 'expected to reduce', 'should fall substantially', and drops the quantitative comparison. It also separates what a monorepo changes (coordinated repository changes and reviews) from what it does not (deployment coordination between independently deployed services), and adds a shared-dependency CI coverage validation to Risks and Next steps as a cutover gate.
- Exactly one recommended option, with no conditional endorsement of another (finding R2-1): the earlier draft named A as the preferred option if coupling turned out weak, which is a second recommendation in disguise and contradicts the task's 'exactly one option'. The memo now recommends B only; if the assumptions fail, the recommendation is withdrawn and the memo is rescored and reissued. Comparisons with A and C remain, because explaining why they lose is part of the reasons, but neither is called preferred, recommended, or a fallback anywhere in the memo. Acceptance criterion 5 was reworded from 'names exactly one option' to 'endorses exactly one option' to match.
- Ownership and access treated as an assumption, not a fact (finding R2-2): the task supplies only team size and service count. Nothing establishes shared ownership, uniform access, or the absence of organisational boundaries, so the categorical 'no team boundary worth mirroring' claim is removed. Shared ownership and uniform access become a third labelled assumption in Context, are checked in Next steps step 1, and the Recommendation may cite them only in the explicitly conditional form. This costs ~25 words, absorbed by the budget.
- Target 460-570 words: still roughly 130 words of margin against both bounds, resilient to small edits in later rounds.

## Non-goals

- Committing or pushing; the deliverable is the file. Branch is `master`; leave git state otherwise untouched.
- Researching real-world monorepo benchmarks or tooling comparisons; the scores are illustrative judgement calls and are labelled as such in the memo's Criteria legend.
- Actually measuring the team's pull-request history, CI configs, or repository permissions; that is the memo's first next step for the team, not something the builder can do with a hypothetical team.
- Creating any other files (README, scripts, templates).
- Multi-page analysis, appendices, or diagrams.
- Writing a contingent second recommendation for the case where the assumptions fail; that case is handled by withdrawing and reissuing the memo, not by pre-selecting another option.
